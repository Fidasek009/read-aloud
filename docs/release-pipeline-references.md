# Open-source extension release pipelines

Reviewed 2026-11-05. Read the actual public workflows, including fresh GitHub API reads; no upstream workflows were executed and no maintainers were contacted. These are examples of implementation choices, not evidence that every detail meets our requirements or that their store submissions currently succeed.

| Extension and inspected workflow | Trigger and artifact flow | Store authentication and publication |
| --- | --- | --- |
| [Refined GitHub](https://github.com/refined-github/refined-github/blob/cc22fe3434b082a982da1efcfbd4f14b4518c747/.github/workflows/release.yml) | Manual dispatch; builds once, assigns a version, passes artifacts to separate store jobs; creates a draft GitHub release before submissions finish. | Chrome OAuth client/secret/refresh token with chrome-webstore-upload-cli; Firefox API key/secret with web-ext's listed channel. Store-specific GitHub environments. |
| [Violentmonkey](https://github.com/violentmonkey/violentmonkey/blob/6f9e25ca57f346fe3e7e8274cff9616c2cbdd8bd/.github/workflows/release.yml) | `v*` tags or manual dispatch; tests/builds, uploads common artifacts, then separate store and GitHub release jobs. GitHub release depends on build, not store success. | Chrome OAuth client/secret/refresh token; AMO key/secret. Its manual dry-run skips stores but still creates a GitHub release. |
| [Dark Reader](https://github.com/darkreader/darkreader/blob/3df6a4aacb7285859003eb1af3182e4370280b5e/.github/workflows/tagged-release.yml) | `v*` tags or manual dispatch; builds browser archives and attaches them to GitHub releases on tags. | This workflow does not submit to either store; it cannot establish their store-authentication method. |
| [Plex Skipper, a WXT extension](https://github.com/GuiEpi/plex-skipper/blob/2033018ae2934b9ec2aeca89eaa2c4c8b724a815/.github/workflows/deploy.yml) | Main pushes/PRs; package.json changes trigger version handling; WXT ZIPs, sequential submissions, then automatic GitHub release. | Chrome API v2 service-account email/private key; AMO issuer/secret and reviewer source ZIP through WXT. A single-store failure is downgraded to a warning. |

The shared useful pattern is to test/build before distribution, use browser-specific packages, reuse built artifacts, and keep credentials in publishing jobs. Tag triggers and full store automation are established approaches; no single release/version convention or credential mechanism is universal across these examples. Our tag-only version authority, Bun tooling, both-store success requirement, and automatically published GitHub release remain the owner's requirements.

None of these four uses Chrome Workload Identity Federation in the inspected workflow. Google nevertheless [recommends federation over exported keys](https://github.com/google-github-actions/auth#authenticate-to-google-cloud-from-github-actions). Our installed publish-browser-extension 6.2.0, used by WXT 0.21.5, accepts `CHROME_SERVICE_ACCOUNT_ACCESS_TOKEN`; its [configuration reference](https://github.com/aklinker1/publish-browser-extension/blob/main/docs/config-reference.md#chromeserviceaccountaccesstoken) documents that short-lived token input. We can use the existing WXT submission path without maintaining a second store API client.

For Firefox, WXT's current publisher uses V5 but requires an existing add-on. Mozilla supports [automated initial listings and updates](https://extensionworkshop.com/documentation/publish/signing-and-distribution-overview/) through `web-ext` 8+ or V5 directly. Our [Firefox setup](firefox-publishing-setup.md) now uses Mozilla's pinned `web-ext` client for both cases, with the same AMO issuer/secret. Dark Reader's inspected workflow builds GitHub release artifacts; it does not establish how its maintainers submit to AMO.

Chosen setup: GitHub OIDC → Google federation → impersonated service account authorized in Chrome → a short-lived Web Store-scoped access token → WXT submit. Google credentials are minted independently in preflight and live Chrome publication after dependency installation/artifact download. Firefox retains its supported API issuer/secret flow. This is a recommendation based on current official authentication guidance and supported tooling, not a claim that federation is already universal among extensions. See [setup instructions](chrome-publishing-setup.md).
