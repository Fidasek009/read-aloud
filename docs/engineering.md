# Engineering baseline

Updated: **2026-11-03**. This documents the development prototype, not release readiness. See [acceptance status](feasibility-status.md) for measured results and open gates, and [research](research.md) for dated source material.

## Toolchain

Use WXT 0.21.5, strict TypeScript, explicit Manifest V3 builds for Chrome and Firefox, and Bun 1.4.4 for package management, scripts, tests, native checking, and formatting. Keep a single frozen Bun lockfile. Browser code must not depend on development-only Bun APIs. Relevant upstream guidance: [WXT project structure](https://wxt.dev/guide/essentials/project-structure.html), [browser targets](https://wxt.dev/guide/essentials/target-different-browsers.html), [Bun checking](https://bun.com/docs/runtime/check), and [Bun formatting](https://bun.com/docs/format).

`bun run typecheck` checks page, worker, tool, and test environments; `bun run test` runs the product tests in `tests/`. `bun run format:check` checks repository formatting. Build the two browser targets with `bun run build` and `bun run build:firefox`.

## Product architecture

The context menus invoke selection or article reading. Web pages host a compact extension iframe; the source content script retains text-to-DOM mappings. A separate extension tab renders PDFs through bundled PDF.js, retains source offsets, and prepares visible canvas/text layers on demand. PDF control requests use separate session-storage keys, per-reader serialization, and explicit acknowledgements; timeouts and reader closure fail the request. PDF text extraction and native-viewer handoff remain performance and correctness concerns; see the acceptance status. Site-specific access can be requested after a PDF fetch fails, using an explicit user gesture and optional host permissions. Sources: [PDF.js API](https://mozilla.github.io/pdf.js/api/draft/module-pdfjsLib.html), [Chrome permissions](https://developer.chrome.com/docs/extensions/develop/concepts/declare-permissions), and [Mozilla optional host permissions](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/optional_host_permissions).

The playback bar provides sentence navigation, voice, speed, volume, and close. Speed and volume use native floating popovers. Volume affects a smoothed output gain, while speed controls model duration. Playback uses a discriminated phase state so preparing, selecting, playing, pausing, completion, failure and closure cannot overlap. Selection replaces the reading scope; sentence navigation must not leave it. PDF line-ending normalization preserves mappings to printed source fragments and leaves real inline compounds and domain dots intact.

The selected prototype speech path uses pinned Piper model data, ONNX Runtime Web, and Spellophone/eSpeak NG. Model files and configs are explicitly downloaded, integrity-checked, and stored locally; previews are requested only by deliberate action. The extension requests unlimited and persistent storage for downloaded voices; [Chrome documents](https://developer.chrome.com/docs/extensions/develop/concepts/storage-and-cookies) its eviction protection, and one Firefox probe reported persistent storage after a download. The application source is MIT, while third-party code and data have separate terms. See [licensing](licensing.md) and [NOTICE](../NOTICE.md). Catalog inclusion alone does not establish voice licensing or quality.

A packaged worker synthesizes locally. Chrome uses an offscreen document coordinated through its extension service worker, with the player connected directly to that document; Firefox runs its worker from the extension background page. Audio remains in the reading tab, allowing tab switches while source navigation/closure ends the session. Read-ahead and generation identifiers reject stale results; active inference cancellation still requires scrutiny. Open player ports retain the Chrome host; after the last disconnect its two-minute retention deadline allows idle document closure. A short preparation lease and shared lifecycle lock protect the asynchronous gap before a new player port connects. `bun run probe:host` exercises this using shortened deadlines in a copied test bundle; `HOST_LIFECYCLE_REAL_TIME=1` uses production deadlines. PCM uses structured-clone messages in Firefox and Base64 in Chrome, where compatibility extends before the [Chrome 148 opt-in](https://developer.chrome.com/blog/structured-clone-messaging). See [Chrome offscreen API](https://developer.chrome.com/docs/extensions/reference/api/offscreen) and [Mozilla background scripts](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/Background_scripts).

The CPU worker configures up to four threads only in a cross-origin-isolated context and otherwise configures one. The diagnostic records configured threads, not independent proof of actual thread use. GPU initialization and inference have a CPU fallback; browser API presence is not evidence of correct or fast hardware inference. See [ONNX Runtime thread requirements](https://onnxruntime.ai/docs/tutorials/web/env-flags-and-session-options.html). A rotated Chrome VM experiment covers one model and several sentences; it does not establish optimal graph options across models, devices, or Firefox.

Speaker IDs are supplied per inference so a speaker change within one model reuses its session. `bun run probe:speakers` uses an explicitly provisioned, pinned `en_GB-aru-medium` model and config in `.cache/speaker-fixture/`; it checks integrity and does not download the fixture automatically. The Firefox product probe runs the same check when that fixture is present.

Word highlighting derives timing from predicted acoustic frames and maps it to the original source. Source-specific phonemizer failures may be isolated through bounded recovery; runtime failures and cancellation must not silently discard content. Model and bounded speech caches must not persist reading text in diagnostics or analytics. Diagnostic transport and persistence use explicit metadata/timing allowlists; raw runtime errors and arbitrary strings are excluded.

## Security and accessibility

Bundle executable code and use the extension CSP; user-selected PDF origins and explicit voice downloads are the network exceptions. Keep permissions narrow, validate cross-boundary messages, treat source content as untrusted, and avoid reading text in logs. Follow [Chrome remote-code guidance](https://developer.chrome.com/docs/extensions/develop/migrate/remote-hosted-code), [Mozilla extension policies](https://extensionworkshop.com/documentation/publish/add-on-policies/), and the applicable [WCAG 2.2](https://www.w3.org/TR/WCAG22/) criteria. Keyboard, focus, contrast and assistive-technology checks remain release gates.

## Evidence and limitations

The product and PDF probes under `scripts/` exercise parts of actual Chrome/Firefox builds and the original MUNI thesis, with test instrumentation and grants. They do not establish native operating-system menu behavior, Zen, Windows, physical GPU behavior, all-document reading fidelity, or audible latency on target hardware. The [historical inference experiments](archive/speech-lab/README.md) are preserved in Git. See [acceptance status](feasibility-status.md) and the dated JSON evidence for exact scope.
