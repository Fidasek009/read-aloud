# Cold-start investigation — 2026-11-03

The 2-second cold first-audio target remains unmet. This investigation distinguishes a runtime startup cost from the cost of loading the actual voice; it does not redefine cold startup or hide initialization before the timer.

## What the existing measurement includes

`worker.ts` times `InferenceSession.create` as `sessionMs`. In installed ONNX Runtime Web 1.31.1, the first call initializes the backend, imports/instantiates WebAssembly, initializes ORT, then loads the model. The current number therefore does **not** identify graph optimization alone as the cause. See installed `lib/backend-wasm.ts`, `lib/wasm/proxy-wrapper.ts`, `lib/wasm/wasm-factory.ts`, and `lib/wasm/wasm-core-impl.ts`.

The development-only [phase probe](../scripts/probe-cold-phases.ts) compares the production path with a path that creates/releases a tiny Identity session immediately before the voice session. Both paths use fresh workers; total load and first-buffer timings include the tiny session. `runtimeAndTinySessionMs` is an upper bound on runtime initialization, while the split sample's `sessionMs` isolates subsequent real-model loading in the initialized runtime. Two rotated rounds reduce simple order bias but cannot establish target-device performance. See [results](evidence/cold-phases-2026-11-03.json).

## Measured split

On this Chrome 155 development VM, the tiny-session/runtime phase took 268–349 ms; loading the real voice in that initialized runtime still took 5,428–5,516 ms. Baseline session creation took 6,048 and 5,391 ms. Inclusive first-buffer timings were 6,296/6,421 ms for split samples and 6,671/5,904 ms for baseline samples. All four noise-disabled PCM hashes matched; the probe checked six aligned-word records per sample but did not compare every alignment timestamp.

These samples point to large-model session construction as the dominant cost. The split is diagnostic, not a production optimization: it does not improve the measured cold path consistently. The first baseline includes the first possible WASM compilation; the later samples can benefit from the browser's compilation cache. All samples use fresh workers and the copied current Chrome production manifest, with reported cross-origin isolation and four configured threads. This is not verification of actual worker-thread utilization or performance on the target four-core device.

## Model preparation options

ONNX Runtime officially supports loading ORT-format models through its Web JavaScript API, and describes the format as a route to faster initialization. Preoptimized model data is the most promising preparation experiment if actual-model loading dominates. This remains a hypothesis until measured with this model, alignment output, both browsers and CPU/GPU paths. [ORT format](https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-models.html), [Web deployment](https://onnxruntime.ai/docs/tutorials/web/build-web-app.html).

There is no ready silent conversion API in the shipped Web runtime. Its common TypeScript interface advertises `optimizedModelFilePath`, but the pinned Web build explicitly sets `FILESYSTEM=0`; native serialization writes to a file. A stale popup comment does not establish a usable export path. The documented converter uses Python, which is outside this project's Bun-only toolchain. Do not add that dependency implicitly or promise browser-side conversion from the session option. [Pinned build flags](https://github.com/microsoft/onnxruntime/blob/v1.31.1/cmake/onnxruntime_webassembly.cmake#L209-L224), [pinned serializer](https://github.com/microsoft/onnxruntime/blob/v1.31.1/onnxruntime/core/session/inference_session.cc#L1042-L1075).

A future maintainer conversion pipeline would need reproducible pinned tooling, hashes and license provenance for each prepared voice, duration-output instrumentation before conversion, and a storage-format/runtime compatibility key. CPU-specific optimized assets must not be reused blindly for WebGPU. Offline layout optimizations can depend on the target environment. [Optimization portability](https://onnxruntime.ai/docs/performance/model-optimizations/graph-optimizations.html#onlineoffline-mode).

The pinned LJSpeech export has 6,423 nodes, including 2,578 `Constant` nodes, and 350 initializers. However, ORT already converts Constant nodes into initializers and removes them during graph construction. Adding a first-party Constant-lifting pass would duplicate runtime behavior and is not justified as the cold-start solution. [Pinned graph construction](https://github.com/microsoft/onnxruntime/blob/v1.31.1/onnxruntime/core/graph/graph.cc#L1198-L1244).

External weights do not inherently reduce graph construction or kernel preparation. Installed Web `createSession` loads and mounts `externalData` before creating the session. Streaming Blob-backed external data is specific to JSPI builds; it is not the runtime packaged by this extension. Splitting a 63 MB voice into files should not be presented as a latency fix without measurements.

`session.use_ort_model_bytes_directly` is already enabled by default in the installed Web session-options adapter. Its initializer-sharing companion concerns ORT-format data; adding either flag to the existing ONNX path is not an established improvement. [ORT loading and memory options](https://onnxruntime.ai/docs/performance/model-optimizations/ort-format-models.html#ort-format-model-loading).

## Bun-only maintainer conversion experiment

A separate [maintainer probe](../scripts/probe-ort-format.ts) successfully loads the upstream `onnxruntime-node` 1.31.1 N-API6 binary under Bun 1.4.4. This uses Bun's native-addon interface; it does not invoke a Node or Python executable. The experiment verifies the pinned package SHA-512, extracts only the Linux x64 binding and JavaScript adapter, reuses the existing pinned common package, and never runs upstream install scripts. The upstream postinstall downloads optional CUDA binaries; CPU binaries are already in the package. Root dependency manifests and the lockfile are unchanged. This establishes compatibility for this specific experiment, not general native-addon compatibility. [Bun Node-API](https://bun.com/docs/runtime/node-api), [upstream binding](https://github.com/microsoft/onnxruntime/blob/v1.31.1/js/node/lib/binding.ts).

The native CPU converter retains the instrumented duration output and uses basic graph optimization, without hardware-specific layout optimizations. It produced a 64,184,632-byte ORT file from the 63,531,605-byte instrumented ONNX file. Conversion took 5.19 seconds in the final run and occurs only in this maintainer experiment, outside browser startup. The ignored cache contains package provenance and copies of the existing runtime MIT license and third-party notices. The prepared model retains its separate obligations and has **not** been published or vetted for distribution.

The browser experiment used two rounds, reversing four variants in the second round. ONNX/basic first buffer took 6.80–6.94 seconds. ORT/basic took 5.23–5.53 seconds. ORT with runtime optimization disabled took 4.98–5.02 seconds with prepacking enabled, and 5.04–5.19 seconds with prepacking disabled. Real session creation still took roughly 4.4–4.7 seconds for all ORT variants. Every sample produced byte-identical noise-disabled PCM and identical full word-alignment records for the fixed sentence. See [complete results and limits](evidence/ort-format-2026-11-03.json).

This shows a measurable improvement from prepared assets but **does not meet the 2-second cold target**. The variant differences are too small and the sample too narrow to establish a production default. No Firefox, physical GPU, Windows, full-catalog, audible-quality or target-device acceptance follows from this Chrome CPU experiment. Production code, voice downloads, and packaged dependencies remain unchanged.

## Next decision

Use the phase results to choose the next experiment. Actual-model loading dominates these samples, and the first prepared-asset experiment improves it without meeting the target. The next performance investigation should profile the remaining ORT session construction rather than assume another session flag will remove several seconds. If runtime initialization dominates, investigate packaged runtime size and compilation with browser tracing. Keep the first-buffer timer inclusive and compare deterministic audio plus duration alignment. Neither prewarming nor changing to a lower-quality voice meets the cold medium-model requirement by itself. ONNX Runtime documents `env.trace` and verbose logging for diagnosis; capture only model/runtime metadata, never user text. [Performance diagnosis](https://onnxruntime.ai/docs/tutorials/web/performance-diagnosis.html).
